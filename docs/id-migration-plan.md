# 固定 ID 安全迁移方案

## 1. 当前分类和内容 ID 是如何生成的

当前页面未使用显式的数据库主键或固定 ID，而是依赖数组位置生成“逻辑 ID”。

### 分类与内容的当前生成方式

- 在 [js/script.js](../js/script.js) 中，内容 ID 由函数 `id(g, i)` 生成：

```js
function id(g, i) {
  return g + "-" + i;
}
```

- 这里的 `g` 是分类索引，`i` 是内容索引。
- 也就是说，当前实际使用的 ID 形式为：
  - `0-0`
  - `0-1`
  - `1-0`
  - `2-3`
  - …

### 当前数据结构中的实际情况

- 分类对象由 [data/data.js](../data/data.js) 汇总后形成数组 `ORIGINAL_DATA`。
- 页面在运行时把它复制到 `groups`，再通过 `groups[gi].items[ii]` 访问内容。
- 收藏和最近使用记录是通过这些“位置型 ID”保存到 `localStorage` 的：
  - `favs`
  - `recent`

因此，当前 ID 的本质是“数组下标拼接值”，不是稳定主键。

## 2. 为什么调整数组顺序会影响收藏和最近使用

### 根因

当前收藏/最近使用使用的不是固定内容主键，而是由数组位置推导出的逻辑 ID。

例如：

- 原内容 `A` 可能生成 ID `0-2`
- 如果把分类顺序或者内容顺序调整，`A` 可能变成 `1-2` 或 `0-5`

这会导致：

- 用户已收藏的内容在新顺序下无法匹配到正确内容；
- 最近使用记录中的旧 ID 失去对应关系；
- 页面显示时会出现“收藏内容丢失”或“最近使用项指向错误内容”的现象。

### 影响范围

- `favs` 中保存的字符串例如 `0-3`、`2-1`。
- `recent` 中保存的字符串例如 `1-0`、`4-2`。
- 只要分类或内容顺序变动，这些字符串就可能失效。

因此，任何涉及“重排数组”、“插入新分类”、“插入新内容”的修改，都必须先建立固定 ID 再进行迁移。

## 3. 为 7 个分类设计稳定的 `category_id` 命名规则

建议按“业务语义 + 固定前缀”的方式设计，避免依赖数组顺序。

### 推荐规则

- 前缀统一为 `cat_`
- 后跟业务分类缩写，采用小写字母和下划线

### 具体命名

| 分类 | 推荐 `category_id` |
| --- | --- |
| 售前 | `cat_presale` |
| 售后 · on hold 触发 | `cat_aftersale_onhold` |
| 售后 · 处置动作 | `cat_aftersale_actions` |
| 其他 | `cat_other` |
| 产品中心 | `cat_products` |
| 操作教程 | `cat_tutorials` |
| 新人培训 | `cat_training` |

### 规则说明

- 命名稳定，不随数组顺序变化；
- 易于在 SQL、JSON、localStorage 中统一识别；
- 后续数据库表中可直接作为主键或外键。

## 4. 为 29 篇内容设计稳定的 `content_id` 命名规则

### 推荐规则

- 前缀统一为 `content_`
- 由 `category_id` + `_` + 序号组成
- 序号建议使用 3 位数字，避免混淆

### 具体命名方式

```text
content_<category_key>_<001>
```

### 示例

| 分类 | 内容标题示例 | 建议 `content_id` |
| --- | --- | --- |
| 售前 | 客户问”Claude 怎么买”（交底 + 留痕） | `content_cat_presale_001` |
| 售前 | 售前 · Pro（成品号 vs 护航版） | `content_cat_presale_002` |
| 售后 · on hold 触发 | 客户触发 on hold（第一时间 · 复核申诉指引） | `content_cat_aftersale_onhold_001` |
| 售后 · 处置动作 | 退款确认 | `content_cat_aftersale_actions_001` |
| 其他 | 老客户质问旧承诺（“你之前说全程质保 / 永久”） | `content_cat_other_001` |
| 产品中心 | Claude 产品速查 | `content_cat_products_001` |
| 操作教程 | Claude 首次充值 | `content_cat_tutorials_001` |
| 新人培训 | 新人上岗阅读顺序 | `content_cat_training_001` |

### 规则说明

- `content_id` 仅依赖分类和内容顺序，不依赖当前数组位置；
- 后续数据库和前端都能稳定地引用同一条内容；
- 若后续内容重排或新增，仍可保持相对稳定，前提是新增内容时按规则追加编号。

## 5. 迁移时必须兼容现有 localStorage 收藏和最近使用数据

### 当前兼容对象

当前浏览器本地存储里保存的有：

- `zy_kb_favs_v2`：收藏记录
- `zy_kb_recent_v2`：最近使用记录

### 兼容策略

迁移时必须同时考虑以下两类数据：

1. 旧格式：如 `0-2`、`3-1`
2. 新格式：如 `content_cat_presale_003`

### 推荐兼容逻辑

- 页面启动时先读取旧格式 ID；
- 若发现是旧格式，则将其映射为新格式；
- 映射后再写回新的 `localStorage` 结构；
- 旧键名不直接删除，先保留并在下一个版本完成清理。

### 推荐映射步骤

- 维护一份“旧 ID → 新 ID”的映射表；
- 对收藏和最近使用记录逐条转换；
- 如果某条旧 ID 对应不上新数据，降级为“不可解析项”，不直接丢弃，而是保留在日志或临时列表中。

### 兼容目标

- 用户已有收藏与最近使用不丢失；
- 迁移后仍能正确打开对应内容；
- 避免发布后出现“用户收藏突然消失”的问题。

## 6. 推荐分阶段实施

### 阶段 1：先给数据增加固定 ID

#### 目标

- 在现有分类对象和内容对象中增加固定字段，但不改变现有页面展示逻辑。

#### 建议改动

- 给每个分类对象增加：
  - `category_id`
- 给每个内容对象增加：
  - `content_id`
  - `sort_order`

#### 兼容方式

- 保留旧字段 `title`、`paragraphs`、`items` 不变；
- 新字段仅作为补充，先不影响前端渲染。

#### 测试项目

- 验证 7 个分类均有稳定 `category_id`。
- 验证 29 篇内容均有稳定 `content_id`。
- 验证页面仍正常加载。

#### 回滚方法

- 仅新增字段，不删除旧结构；
- 若出现异常，直接回退到无新字段版本即可。

### 阶段 2：页面优先读取固定 ID，并保留旧 ID 兼容

#### 目标

- 页面优先使用固定 ID 进行显示与操作，但仍兼容旧格式。

#### 建议改动

- 在 [js/script.js](../js/script.js) 中，收藏和最近使用逻辑优先使用 `content_id`；
- 如果没有 `content_id`，再退回到旧的 `g-i` 逻辑 ID。

#### 兼容策略

- `favs` 和 `recent` 先支持两种格式：
  - 旧格式：`0-2`
  - 新格式：`content_cat_presale_003`
- 读取时先判断是否为新格式，若不是则转成新格式后再使用。

#### 测试项目

- 旧收藏记录仍能打开对应内容。
- 新收藏记录可写入并正确显示。
- 旧最近使用记录仍可显示。

#### 回滚方法

- 仅在读取逻辑中增加兼容分支；
- 如果出现异常，保留旧逻辑分支即可回退。

### 阶段 3：迁移本地收藏和最近使用

#### 目标

- 把浏览器本地存储中的收藏和最近使用从旧 ID 迁移成固定 ID。

#### 建议改动

- 启动时检测 `zy_kb_favs_v2` 和 `zy_kb_recent_v2`；
- 将旧值逐条映射为新的 `content_id`；
- 写回新格式。

#### 测试项目

- 迁移前后数据条数一致。
- 迁移后对应内容仍可访问。
- 迁移失败时不会丢失原数据。

#### 回滚方法

- 迁移前先备份旧 `localStorage` 键值；
- 若迁移出错，直接恢复备份数据。

### 阶段 4：验证无误后再为 PostgreSQL 做准备

#### 目标

- 确保前端数据结构和 ID 逻辑稳定后，再准备数据库字段与表结构。

#### 建议改动

- 基于统一字段设计生成 SQL 表结构。
- 使用 `category_id`、`content_id` 等字段建表。
- 预留 `created_at`、`updated_at` 等审计字段。

#### 测试项目

- 导入/导出数据时字段映射正确。
- 无重复 `content_id`。
- 可以从前端 JSON 正确映射到数据库字段。

#### 回滚方法

- 仅在准备阶段新增表和字段，不对已有线上数据做破坏性替换；
- 若发现不兼容，先停用新表的写入，继续使用旧结构。

## 7. 每个阶段的测试项目与回滚方法总结

| 阶段 | 重点测试项目 | 回滚方法 |
| --- | --- | --- |
| 阶段 1 | 新字段存在、页面能正常加载 | 不删除旧结构，直接回退 |
| 阶段 2 | 旧收藏和最近使用可兼容打开 | 保留旧逻辑分支，关闭新逻辑 |
| 阶段 3 | 收藏/最近使用迁移后可正常显示 | 从备份恢复 `localStorage` |
| 阶段 4 | PostgreSQL 字段映射与导入导出稳定 | 仅新增表/字段，不替换现有数据 |

## 8. 本步骤说明

本步骤仅写方案，不修改当前网页运行逻辑。

- 不修改 [index.html](../index.html)、[data/data.js](../data/data.js)、[data/*.js](../data)、[js/script.js](../js/script.js) 或 [js/search.js](../js/search.js) 的现有逻辑；
- 不改写任何浏览器存储内容；
- 仅为后续安全迁移提供规范化方案与执行顺序。
